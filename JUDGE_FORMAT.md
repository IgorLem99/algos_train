# Формат тестов задач (`content/judge/*.md`)

Тесты лежат отдельно от условий: `content/judge/<NN-категория>.md`. Файл состоит из блоков,
каждый начинается с front matter `id:` (тот же id, что у задачи), дальше идут fenced-блоки:

| Блок | Обязателен | Что это |
|---|---|---|
| ` ```go starter ` | да | заготовка, которую пользователь видит в редакторе (сигнатура как на LeetCode, пустое тело) |
| ` ```go tests ` | да | Go-код с `func judgeTests(t *Judge)`; пользователю не отдаётся |
| ` ```go types ` | нет | объявления типов, которые на LeetCode «предопределены» (`Node`, `Interval`…). Каждый `type X` добавляется, только если пользователь не объявил `X` сам |

`ListNode` и `TreeNode` объявлены всегда (если пользователь не объявил их сам) — в `types` их не пишут.

````markdown
---
id: two-sum
---
```go starter
func twoSum(nums []int, target int) []int {

}
```

```go tests
func judgeTests(t *Judge) {
	cases := []struct {
		nums   []int
		target int
		want   []int
	}{
		{[]int{2, 7, 11, 15}, 9, []int{0, 1}},
		{[]int{3, 3}, 6, []int{0, 1}},
	}
	for _, c := range cases {
		t.Case(fmt.Sprintf("nums = %v, target = %d", c.nums, c.target), c.want, func() any {
			return twoSum(JClone(c.nums), c.target)
		}, JAnyOrder)
	}
}
```
````

## Как собирается программа

В одну папку кладутся `solution.go` (код пользователя), `judge_tests.go` (блок tests) и
`judge_main.go` (движок из `judgekit/prelude.go` + types). Всё в `package main`;
`package` и импорты стандартной библиотеки (`fmt`, `sort`, `strings`, `strconv`, `math`, `slices`,
`container/heap`, `reflect`…) подставляются автоматически по использованию — писать их не нужно.

## API

```go
// Тест с ожидаемым значением. run вызывает решение и возвращает результат.
t.Case(input string, want any, run func() any, opts ...JOpt)

// Тест с произвольной проверкой — когда правильных ответов несколько.
// want — словесное описание ожидаемого, run возвращает (полученное, вердикт).
t.Check(input, want string, run func() (got any, ok bool))
```

Сравнение в `Case` — по нормализованному представлению:
- все целые типы равны между собой (`[]int{1}` == `[]int64{1}`), nil-срез == пустой срез;
- `*ListNode` → список значений `[1,2,3]`, `*TreeNode` → массив обхода в ширину `[3,9,20,null,null,15,7]`;
- `[]byte` и `byte` → строки (`[][]byte` доска печатается как `["XXO","OXO"]`);
- `[]any{1, "a", true}` удобен для дизайн-задач (результаты нескольких операций).

Опции: `JAnyOrder` — порядок верхнего уровня не важен; `JAnyOrderDeep` — не важен на всех
уровнях (подмножества, перестановки, группы анаграмм); `JFloat` — числа с точностью 1e-5.

Хелперы: `JList(1,2,3)`, `JListVals(head)`, `JListNode(head, i)`, `JTree(3, 9, 20, nil, nil, 15, 7)`,
`JTreeVals(root)`, `JFind(root, val)`, `JClone(slice)`, `JClone2(grid)`, `JBoard("XXO", "OXO")`,
`JShow(v)` — то же форматирование, что в отчёте (для строки input).

## Правила хороших тестов

- **Первые 3 теста — примеры из условия**: кнопка «Запустить» гоняет только их, «Отправить» — все.
- Дальше — крайние случаи (пусто, один элемент, отрицательные, дубликаты, переполнение) и 1–2
  больших теста, на которых квадратичное решение там, где ожидается линейное, заметно
  тормозит, но **все эталонные решения задачи укладываются в лимит** (6 с на все тесты).
- Входные данные, которые решение может изменить, передавай копией (`JClone`, `JClone2`) —
  иначе `want`/следующие тесты испортятся. Каждый `run` строит свои входные данные.
- Строка `input` — короткая и понятная: `nums = [2 7 11 15], target = 9`. Для больших тестов —
  описание (`nums = 0..99999`), а не сам массив.
- Дизайн-задачи (`MinStack`, `LRUCache`…): последовательность операций в одном `Case`, ответ —
  срез результатов; плюс тест со случайными операциями против простой модели.
