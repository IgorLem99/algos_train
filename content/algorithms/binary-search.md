## Суть за 30 секунд

Если данные упорядочены, одно сравнение с серединой отбрасывает половину кандидатов. За `⌈log₂ n⌉` шагов остаётся один элемент: миллиард элементов — около 30 сравнений.

Главная идея шире, чем «найти число в массиве»: бинарный поиск находит **границу монотонного предиката** — первую позицию, где условие становится истинным (`false false … false true true … true`). Так ищут и позицию вставки, и минимальную скорость, при которой успеваем, и момент, когда сломался билд.

## История

- **1946** — Джон Мокли (один из создателей ENIAC) упомянул бинарный поиск в лекциях Moore School — это считается первым публичным описанием.
- **1960** — Деррик Лемер опубликовал вариант, корректно работающий для любого n, а не только для `n = 2^k − 1` (по Кнуту, TAOCP, том 3).
- **1986** — Джон Бентли в «Programming Pearls» рассказал, что при проверке на курсах большинство профессиональных программистов написали бинарный поиск с ошибкой.
- **2006** — Джошуа Блох в блоге Google Research («Nearly All Binary Searches and Mergesorts are Broken») показал, что `mid = (low + high) / 2` переполняется на массивах больше 2³⁰ элементов; ошибка годами жила в `Arrays.binarySearch` из JDK.

## Как работает

Классический поиск значения `t`:

1. `L = 0`, `R = n − 1` — отрезок, где может быть ответ.
2. `mid = L + (R − L) / 2`.
3. `a[mid] == t` — нашли. `a[mid] < t` — ответ правее: `L = mid + 1`. Иначе — левее: `R = mid − 1`.
4. Если `L > R`, элемента нет.

В визуализации ищем 23: `mid = 4` (16 < 23) → вправо; `mid = 7` (56 > 23) → влево; `mid = 5` — нашли за 3 сравнения.

**Шаблон «поиск границы»** надёжнее и универсальнее. Работаем с полуинтервалом `[lo, hi)` и предикатом `ok(i)`, который монотонен: сначала `false`, потом `true`.

- Инвариант: всё левее `lo` — `false`, всё начиная с `hi` — `true`.
- `ok(mid)` истинно → граница в `mid` или левее: `hi = mid`.
- Иначе → граница правее: `lo = mid + 1`.
- Цикл `for lo < hi` завершается, когда `lo == hi` — это и есть первая `true`-позиция (или `n`, если `true` нет).

С этим шаблоном не нужно помнить, где `<=`, а где `<`: меняется только предикат. `a[i] >= x` — lower bound, `a[i] > x` — upper bound, «за `k` часов успеваем?» — бинарный поиск по ответу.

## Шаблон на Go

```go
// lowerBound — первый индекс i, где a[i] >= x (len(a), если такого нет).
func lowerBound(a []int, x int) int {
	lo, hi := 0, len(a) // ответ всегда в [lo, hi]
	for lo < hi {
		mid := int(uint(lo+hi) >> 1) // как в sort.Search: без переполнения
		if a[mid] >= x {
			hi = mid
		} else {
			lo = mid + 1
		}
	}
	return lo
}

// Бинарный поиск по ответу (Koko Eating Bananas): минимальная
// скорость k, при которой все кучи съедаются не более чем за h часов.
func minEatingSpeed(piles []int, h int) int {
	lo, hi := 1, slices.Max(piles)
	for lo < hi {
		k := lo + (hi-lo)/2
		hours := 0
		for _, p := range piles {
			hours += (p + k - 1) / k // деление с округлением вверх
		}
		if hours <= h {
			hi = k // k подходит — пробуем меньше
		} else {
			lo = k + 1
		}
	}
	return lo
}
```

Стандартная библиотека Go:

```go
func stdlibSearch() {
	a := []int{2, 5, 8, 12, 16, 23, 38}

	// sort.Search(n, f): наименьший i в [0, n), где f(i) == true; n, если нет.
	i := sort.Search(len(a), func(i int) bool { return a[i] >= 12 }) // 3

	// slices.BinarySearch (Go 1.21+): позиция и флаг «найден».
	j, found := slices.BinarySearch(a, 13) // 4, false — куда вставлять

	// С собственным сравнением, например для структур.
	type tick struct{ ts int64 }
	ticks := []tick{{10}, {20}, {30}}
	k, _ := slices.BinarySearchFunc(ticks, int64(25), func(t tick, ts int64) int {
		return cmp.Compare(t.ts, ts)
	}) // 2 — первый тик не раньше 25

	fmt.Println(i, j, found, k)
}
```

`sort.Search` — ровно шаблон «первая `true`» и внутри считает середину как `int(uint(i+j) >> 1)`, чтобы не переполниться. `sort.SearchInts`/`SearchStrings` — его обёртки. Если элемента нет, `slices.BinarySearch` возвращает позицию вставки — удобно для `slices.Insert`.

## Сложность

| операция | время | память |
| --- | --- | --- |
| поиск в отсортированном массиве | O(log n) | O(1) |
| lower/upper bound | O(log n) | O(1) |
| поиск по ответу в диапазоне [lo, hi] с проверкой за O(C) | O(C · log(hi − lo)) | зависит от проверки |
| бисекция на вещественных числах до точности ε | O(log((hi − lo)/ε)) | O(1) |
| вставка в отсортированный срез | O(log n) поиск + O(n) сдвиг | O(1) |

## Когда применять

- Массив **отсортирован** (или отсортирован, но повёрнут — Search in Rotated Sorted Array).
- Нужно «первое / последнее вхождение», «позиция вставки», «сколько элементов меньше x».
- «Минимальное значение, при котором можно…» или «максимальное, при котором ещё…» — **бинарный поиск по ответу**: проверка монотонна (если скорость k подходит, то и k+1 подходит).
- Ограничения вида `n ≤ 10⁵`, а значения до `10⁹` — намёк, что перебирать ответ надо логарифмически.
- Поиск пика, минимума в повёрнутом массиве, медианы двух массивов — бинарный поиск по «половине, где точно есть ответ».
- Вещественный ответ (корень, время столкновения) — бисекция фиксированное число итераций.

## Где применяется в реальном мире

### Бигтех
- **git bisect**: разработчик помечает «хороший» и «плохой» коммиты, git бинарным поиском по истории находит коммит, внёсший баг, за `log₂(коммитов)` проверок.
- **B+-деревья в СУБД**: внутри страницы индекса ключи отсортированы, нужный дочерний указатель ищется бинарным поиском (в PostgreSQL — функция `_bt_binsrch`).
- **LevelDB/RocksDB**: в SST-файле бинарный поиск выбирает блок по index block, затем — по restart points внутри блока.
- **Kafka**: чтобы найти сообщение по offset, брокер выбирает сегмент лога по базовому offset и ищет позицию в разреженном файле `.index` бинарным поиском.
- **Linux kernel**: `lib/bsearch.c`; например, таблица исключений (exception table) отсортирована и просматривается бинарным поиском при обработке page fault в ядре.

### Финтех
- **Implied volatility**: цена опциона по Блэку–Шоулзу монотонно растёт с волатильностью, поэтому σ по рыночной цене находят бисекцией или методом Ньютона с бисекцией как страховкой.
- **Временные ряды тиков**: котировки отсортированы по времени — «первый тик после момента t» и границы свечи находятся бинарным поиском.
- **Тарифные шкалы**: ступени комиссий, налоговых ставок, лимитов отсортированы — нужная ступень = upper bound по сумме.
- **Кривые доходности**: при интерполяции ставки на произвольный срок бинарный поиск находит два ближайших узла кривой.

### Геймдев
- **Анимация**: в треке ключевых кадров, отсортированном по времени, бинарный поиск находит пару кадров вокруг текущего момента для интерполяции.
- **Взвешенный лут**: префиксные суммы весов + бинарный поиск случайного числа.
- **Continuous collision detection**: бисекция по времени между «ещё не пересекаются» и «уже пересекаются» находит момент контакта.
- **Поиск регрессий в билдах**: автоматический бисект по сборкам в CI, чтобы найти коммит, уронивший FPS или сломавший тест, — распространённая практика.

## Типичные ошибки

- **Переполнение `(lo + hi) / 2`** — используйте `lo + (hi−lo)/2` или `int(uint(lo+hi) >> 1)`.
- **Бесконечный цикл**: `lo = mid` при `mid = (lo+hi)/2` и `hi = lo + 1` — `mid` равен `lo`, отрезок не сужается. В полуинтервальном шаблоне всегда `lo = mid + 1`.
- **Смешение стилей**: закрытый `[L, R]` требует `L <= R` и `R = mid − 1`, полуоткрытый `[lo, hi)` — `lo < hi` и `hi = mid`. Перемешаете — получите off-by-one.
- **Немонотонный предикат**: бинарный поиск по ответу работает только если «подходит k ⇒ подходит k+1».
- **Неотсортированные данные** — результат молча неверен.
- **Граница `hi` в поиске по ответу** слишком мала (ответ не входит в диапазон) или вычисления внутри проверки переполняются.
- **Вещественные числа**: условие `hi − lo > eps` при больших значениях может никогда не выполниться из-за точности — надёжнее фиксированные 100 итераций.
