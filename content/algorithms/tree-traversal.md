## Суть за 30 секунд

Обойти дерево — значит посетить каждый узел ровно один раз. Способов по сути два. **DFS (поиск в глубину)** ныряет по одной ветке до листа и только потом отступает — как человек в лабиринте с правилом «иди, пока можешь, потом возвращайся». **BFS (поиск в ширину)** идёт слоями: корень, потом все его дети, потом все внуки — как круги на воде.

DFS хранит путь от корня до текущего узла в **стеке** (обычно это стек вызовов рекурсии), BFS хранит «фронт» текущего уровня в **очереди**. Почти любая задача на деревья — это один из этих обходов плюс немного логики в правильный момент посещения узла.

## История

Обход в глубину старше компьютеров: в XIX веке во Франции был описан метод Тремо для прохождения лабиринтов — по сути DFS с пометками на пройденных коридорах; его пересказывает, например, Эдуард Люка в «Математических развлечениях» (1882).

Обход в ширину открывали несколько раз независимо: Конрад Цузе описал его в 1945 году (работа была опубликована намного позже), Эдвард Мур в 1959-м применил его для поиска кратчайшего пути в лабиринте, а Ч. Й. Ли в 1961-м — для трассировки проводников на печатных платах.

Названия pre-order / in-order / post-order закрепились благодаря учебникам 1960-х, прежде всего первому тому «Искусства программирования» Кнута (1968); кто первым ввёл сами термины, сказать трудно. Систематическое применение DFS к графам в 1970-х развили Роберт Тарьян и Джон Хопкрофт.

## Как работает

### DFS: три порядка

Рекурсивная функция для узла делает три вещи: обходит левое поддерево, обходит правое и «посещает» сам узел. От того, **когда** посещается узел, зависит порядок:

- **Pre-order** (узел → левое → правое): родитель раньше детей. Копирование и сериализация дерева, печать дерева каталогов, передача данных «сверху вниз» (сумма на пути, допустимый диапазон).
- **In-order** (левое → узел → правое): для двоичного дерева поиска выдаёт ключи **по возрастанию**. Валидация BST, k-й минимум, BST-итератор.
- **Post-order** (левое → правое → узел): дети раньше родителя. Нужен, когда ответ узла собирается из ответов детей: высота, диаметр, сумма поддерева, сбалансированность, удаление дерева, вычисление выражения.

Ниже — in-order обход BST. Следите за панелью «стек вызовов»: это ровно путь от корня до текущего узла. Его глубина не превышает высоту дерева h — отсюда память O(h).

Рекурсию всегда можно заменить явным стеком. Для pre-order это тривиально (достали узел, положили правого ребёнка, потом левого). Для in-order — «спускайся влево до упора, достань узел, перейди в правое поддерево». Post-order проще всего получить как pre-order в порядке «узел → правое → левое», развёрнутый в конце.

Удобная ментальная модель: обведите дерево по контуру, начиная слева от корня. Каждый узел вы встретите до трёх раз — при входе, между детьми и при выходе. Pre-, in- и post-order — это просто «записать узел при первой, второй или третьей встрече».

### BFS: по уровням

Очередь (FIFO) гарантирует, что все узлы глубины d будут обработаны раньше любого узла глубины d+1. Главный приём — зафиксировать `n := len(queue)` в начале итерации: ровно эти n элементов и есть текущий уровень. Так решаются Level Order Traversal, Right Side View, Zigzag, «среднее по уровням», минимальная глубина (BFS останавливается на первом же листе, а DFS обошёл бы всё дерево).

## Шаблон на Go

`TreeNode` — как на LeetCode: `type TreeNode struct { Val int; Left, Right *TreeNode }`.

```go
// Рекурсивный DFS: порядок определяется тем, где стоит visit.
func inorder(root *TreeNode, visit func(int)) {
	if root == nil {
		return
	}
	inorder(root.Left, visit)
	visit(root.Val) // pre-order — до рекурсивных вызовов, post-order — после обоих
	inorder(root.Right, visit)
}

// Итеративный in-order: явный стек вместо стека вызовов.
func inorderIter(root *TreeNode) []int {
	var res []int
	var stack []*TreeNode
	cur := root
	for cur != nil || len(stack) > 0 {
		for cur != nil { // спускаемся влево до упора
			stack = append(stack, cur)
			cur = cur.Left
		}
		cur = stack[len(stack)-1]
		stack = stack[:len(stack)-1]
		res = append(res, cur.Val)
		cur = cur.Right
	}
	return res
}
```

```go
// BFS по уровням: фиксируем размер уровня до того, как добавляем детей.
func levelOrder(root *TreeNode) [][]int {
	if root == nil {
		return nil
	}
	var levels [][]int
	queue := []*TreeNode{root}
	for len(queue) > 0 {
		n := len(queue)
		level := make([]int, 0, n)
		for _, node := range queue[:n] {
			level = append(level, node.Val)
			if node.Left != nil {
				queue = append(queue, node.Left)
			}
			if node.Right != nil {
				queue = append(queue, node.Right)
			}
		}
		queue = queue[n:]
		levels = append(levels, level)
	}
	return levels
}
```

Детали Go, которые полезно знать:

- Стек горутины начинается с нескольких килобайт и растёт динамически (копированием), поэтому глубокая рекурсия в Go не падает так рано, как в Python с его лимитом рекурсии. Но предел есть: по умолчанию максимум стека — 1 ГБ на 64-битных системах (`debug.SetMaxStack`), после чего программа аварийно завершается. Для «палки» из миллиона узлов надёжнее явный стек.
- В стандартной библиотеке обходы встречаются постоянно: `filepath.WalkDir` — DFS по дереву каталогов в лексическом порядке, `go/ast.Inspect` — pre-order DFS по синтаксическому дереву (после детей узла колбэк вызывается с `nil` — это сигнал «выхода», т.е. post-order-момент).
- `queue = queue[n:]` не освобождает начало массива сразу, но при следующих `append` срез переаллоцируется, так что для обходов деревьев это нормально.
- Начиная с Go 1.23 обход удобно отдавать наружу как итератор `iter.Seq[int]` и потреблять через `for v := range tree.All()`.

## Сложность

| Операция | Время | Память |
|---|---|---|
| DFS (рекурсия или явный стек) | O(n) | O(h): от O(log n) для сбалансированного дерева до O(n) для «палки» |
| BFS по уровням | O(n) | O(w) — ширина самого широкого уровня, до n/2 у полного дерева |
| Обход Морриса (in-order без стека) | O(n) | O(1), но временно перешивает указатели дерева |

## Когда применять

- «Для каждого узла посчитать что-то по его поддереву» (высота, сумма, баланс, диаметр, LCA) → **post-order DFS**, функция возвращает значение наверх.
- «Передать информацию от корня вниз» (путь, сумма на пути, допустимый диапазон значений) → **pre-order DFS** с параметрами.
- «Отсортированный порядок», «k-й наименьший», «проверить, что это BST» → **in-order**.
- «По уровням», «каждый уровень», «вид справа», «минимальная глубина», «ближайший лист» → **BFS**.
- «Сериализовать / восстановить дерево» → pre-order с маркерами `nil` или BFS.

Типичные вариации: DFS, который возвращает одно значение, а глобально обновляет другое (диаметр: возвращаем высоту, обновляем максимум суммы двух высот); BFS с индексом колонки (Vertical Order); зигзаг через чередование направления; обход Морриса, когда просят O(1) памяти.

## Где применяется в реальном мире

### Бигтех
- **Браузеры:** DOM — это дерево; `querySelectorAll` возвращает элементы в «document order», который определён как pre-order обход в глубину. Пересчёт стилей и layout тоже обходят дерево рендеринга.
- **Компиляторы и линтеры:** `go vet`, `gofmt`, staticcheck обходят AST через `go/ast.Inspect` / `ast.Walk`. Генерация кода для выражения — post-order: сначала вычисляем операнды, потом операцию.
- **Файловые системы:** `find`, `du`, `filepath.WalkDir` — DFS по дереву каталогов; `du` по сути post-order: размер каталога = сумма размеров детей.
- **React:** reconciliation обходит дерево fiber-узлов в глубину — `beginWork` при спуске к ребёнку и `completeWork` при подъёме (те самые «вход» и «выход» из pre-/post-order).

### Финтех
- **Merkle-деревья:** корень хешей транзакций в заголовке блока Bitcoin считается снизу вверх — хеш узла зависит от хешей детей, это post-order. Доказательство включения транзакции — путь от листа к корню.
- **Иерархии счетов и юрлиц:** баланс синтетического счёта или холдинга = сумма по дочерним субсчетам/компаниям — агрегация post-order обходом (общая практика бухгалтерских и treasury-систем).
- **Движки правил и скоринга:** условие вида «сумма > 10 000 И (страна ∈ X ИЛИ новый девайс)» парсится в дерево выражения и вычисляется post-order обходом; короткое замыкание — это ранний выход из DFS.

### Геймдев
- **Scene graph:** в Unity (иерархия Transform), Godot (SceneTree) и других движках мировая трансформация узла = трансформация родителя × локальная, поэтому иерархия обходится сверху вниз (pre-order): родитель считается раньше детей.
- **Behaviour trees:** на каждом тике ИИ дерево обходится от корня в глубину слева направо; Selector и Sequence вызывают детей по порядку и прерывают обход по Success/Failure.
- **BVH и октодеревья:** raycast и проверка столкновений — DFS по иерархии ограничивающих объёмов с отсечением поддеревьев, чей bounding box не пересекает луч. На GPU это обычно делается на явном стеке, потому что рекурсия там дорогая или недоступна.

## Типичные ошибки

- Нет базового случая `if root == nil { return }` → nil pointer dereference.
- В BFS не зафиксировали `len(queue)` перед циклом уровня — уровни «склеиваются».
- Ожидать отсортированный порядок от in-order у дерева, которое не является BST.
- Вычислять `height()` заново в каждом узле (проверка сбалансированности, диаметр) → O(n²). Нужен один post-order обход, который возвращает высоту наверх.
- Итеративный pre-order: положить в стек сначала левого ребёнка, потом правого — получится зеркальный порядок.
- Пакетная переменная-аккумулятор для рекурсии, которую забыли сбросить между вызовами: на LeetCode тесты идут подряд в одном процессе, и ответ «протекает» в следующий тест. Лучше замыкание внутри функции.
