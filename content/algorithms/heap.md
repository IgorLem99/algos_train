## Суть за 30 секунд

Двоичная куча — это полное двоичное дерево, в котором **каждый родитель не больше своих детей** (min-heap) или не меньше (max-heap). Порядок между братьями не важен — гарантируется только, что минимум лежит в корне. Этого «частичного порядка» хватает, чтобы доставать минимум за O(log n) и добавлять элементы за O(log n), и он намного дешевле полной сортировки.

Аналогия — приёмный покой больницы: пациентов принимают не в порядке прихода, а по срочности, и новый тяжёлый пациент сразу «всплывает» наверх очереди. Очередь с приоритетом — это интерфейс («дай самый срочный»), а куча — самая популярная его реализация. Почти все задачи «top-K», «слияние K списков», «медиана потока», а также алгоритмы Дейкстры и Прима стоят на куче.

## История

- **1964** — Дж. У. Дж. Уильямс опубликовал heapsort (Algorithm 232 в Communications of the ACM) и вместе с ним двоичную кучу как структуру данных.
- **1964** — Роберт Флойд в том же году улучшил алгоритм (TREESORT 3): кучу можно построить из массива на месте за O(n), просеивая вниз элементы от середины массива к началу.
- **1975** — d-арные кучи (у узла d детей) применил Дональд Джонсон для ускорения алгоритмов кратчайших путей.
- **1984** — Майкл Фредман и Роберт Тарьян предложили фибоначчиеву кучу с амортизированным O(1) на уменьшение ключа, что улучшило теоретическую оценку алгоритма Дейкстры. На практике её почти не используют — константы слишком велики.

Слово «куча» здесь не связано с «кучей» как областью динамической памяти (heap в смысле `malloc` и escape analysis в Go) — это просто совпадение названий.

## Как работает

**Хранение в массиве.** Дерево полное (заполняется слева направо, уровень за уровнем), поэтому указатели не нужны: у элемента с индексом `i` дети — `2i+1` и `2i+2`, родитель — `(i−1)/2`. Никаких дыр, отличная кэш-локальность.

**Push (просеивание вверх, sift-up).** Кладём новый элемент в конец массива — дерево остаётся полным. Затем, пока элемент меньше родителя, меняем их местами. Высота дерева ⌊log₂ n⌋, значит не больше log n обменов.

**Pop (просеивание вниз, sift-down).** Минимум — в `a[0]`. Забираем его, на освободившееся место ставим последний элемент массива и «топим» его: пока он больше хотя бы одного ребёнка, меняем с **меньшим** из детей. Снова не больше log n шагов.

**Peek** — просто `a[0]`, O(1).

В визуализации в min-heap по очереди вставляются 5, 3, 8, 1, 9, 2 (смотрите, как 1 всплывает до корня за два обмена), а затем извлекается минимум.

**Построение кучи из массива за O(n).** Вставлять n элементов по одному — O(n log n). Но если просеять вниз все внутренние узлы, начиная с `n/2−1` и до 0, выйдет O(n): большинство узлов находится внизу и тонет на 0–1 уровень. Именно так работает `heap.Init`.

**Max-heap** — та же структура с обратным сравнением. Кучу по убыванию в Go получают, перевернув `Less`.

## Шаблон на Go

В стандартной библиотеке есть `container/heap`. Он не содержит данных — это набор алгоритмов над вашим типом, реализующим `heap.Interface`: `sort.Interface` (`Len`, `Less`, `Swap`) плюс `Push(x any)` и `Pop() any`. Пакет появился задолго до дженериков, поэтому `any` и приведения типов.

```go
type Item struct {
	Value    string
	Priority int
	index    int // позиция в куче — нужна для heap.Fix и heap.Remove
}

// PQ — min-куча по Priority. Push/Pop с указателем: они меняют длину среза.
type PQ []*Item

func (q PQ) Len() int           { return len(q) }
func (q PQ) Less(i, j int) bool { return q[i].Priority < q[j].Priority }
func (q PQ) Swap(i, j int) {
	q[i], q[j] = q[j], q[i]
	q[i].index = i
	q[j].index = j
}
func (q *PQ) Push(x any) {
	it := x.(*Item)
	it.index = len(*q)
	*q = append(*q, it)
}
func (q *PQ) Pop() any {
	old := *q
	n := len(old)
	it := old[n-1]
	old[n-1] = nil // не держим ссылку — помогаем GC
	*q = old[:n-1]
	return it
}

// Update меняет приоритет элемента, уже лежащего в куче, за O(log n).
func (q *PQ) Update(it *Item, priority int) {
	it.Priority = priority
	heap.Fix(q, it.index)
}

func demo() string {
	q := &PQ{}
	heap.Push(q, &Item{Value: "b", Priority: 2}) // heap.Push, а не q.Push!
	a := &Item{Value: "a", Priority: 5}
	heap.Push(q, a)
	q.Update(a, 1)
	return heap.Pop(q).(*Item).Value // "a"
}
```

Та же логика вручную — полезно уметь написать на собеседовании и быстрее на горячем пути (нет интерфейсных вызовов):

```go
type MinHeap struct{ a []int }

func (h *MinHeap) Len() int  { return len(h.a) }
func (h *MinHeap) Peek() int { return h.a[0] }

func (h *MinHeap) Push(x int) {
	h.a = append(h.a, x)
	i := len(h.a) - 1
	for i > 0 {
		p := (i - 1) / 2
		if h.a[p] <= h.a[i] {
			break
		}
		h.a[p], h.a[i] = h.a[i], h.a[p]
		i = p
	}
}

func (h *MinHeap) Pop() int {
	top := h.a[0]
	last := len(h.a) - 1
	h.a[0] = h.a[last]
	h.a = h.a[:last]
	for i := 0; ; {
		l, r, m := 2*i+1, 2*i+2, i
		if l < len(h.a) && h.a[l] < h.a[m] {
			m = l
		}
		if r < len(h.a) && h.a[r] < h.a[m] {
			m = r
		}
		if m == i {
			break
		}
		h.a[m], h.a[i] = h.a[i], h.a[m]
		i = m
	}
	return top
}
```

Где куча живёт внутри Go: таймеры runtime (`time.Sleep`, `time.After`, `time.AfterFunc`, дедлайны `context`) хранятся в **4-арной min-куче** на каждом P (логическом процессоре планировщика), упорядоченной по времени срабатывания. 4-арная куча ниже двоичной, поэтому просеивание вверх короче, а дети узла лежат рядом в памяти.

## Сложность

| Операция | Время | Память |
|---|---|---|
| Peek (min/max) | O(1) | — |
| Push | O(log n) | O(1) амортизированно |
| Pop | O(log n) | — |
| `heap.Init` (построение из массива) | O(n) | O(1) доп. |
| `heap.Fix` / `heap.Remove` по индексу | O(log n) | — |
| Поиск произвольного элемента | O(n) | — |
| Heapsort | O(n log n) | O(1) доп. |

## Когда применять

- **«K наибольших / наименьших», «top-K частых»** → куча размера K. Хитрость: для K **наибольших** держим **min**-кучу размера K и выбрасываем минимум при переполнении — получаем O(n log K) вместо O(n log n).
- **«Слить K отсортированных списков/потоков»** → куча из K «голов» потоков.
- **«Медиана потока»** → две кучи: max-куча для нижней половины и min-куча для верхней, размеры отличаются не больше чем на 1.
- **«Постоянно нужен минимум/максимум, а данные меняются»**: планирование задач по времени, переговорные комнаты (min-куча по времени окончания), Task Scheduler, IPO.
- **Графы:** Дейкстра, Прим, A* — очередь с приоритетом по расстоянию.

Вариации: ленивое удаление (помечаем элемент удалённым и пропускаем его при Pop), индексированная куча с `heap.Fix`, две кучи, куча пар `(значение, индекс)`, k-way merge.

## Где применяется в реальном мире

### Бигтех
- **Go runtime:** 4-арная куча таймеров на каждом P; планировщик проверяет её корень, чтобы понять, когда сработает ближайший таймер.
- **Kubernetes:** в kube-scheduler `activeQ` — куча подов, ожидающих планирования; на вершине под с наивысшим приоритетом (при равенстве — более ранний).
- **Node.js / libuv:** таймеры event loop хранятся в двоичной min-куче; на каждой итерации цикл берёт ближайший дедлайн, чтобы понять, сколько можно спать в `epoll`/`kqueue`.
- **Хранилища и поиск:** RocksDB и LevelDB при чтении и компакции сливают отсортированные файлы (SSTable) через k-way merge на куче; Lucene собирает top-N документов по релевантности в `PriorityQueue`.

### Финтех
- **Биржевой стакан:** лучшая цена покупки — максимум, продажи — минимум, и их нужно знать мгновенно. Кучи по ценовым уровням дают O(1) на «лучшую цену», но отмена заявки из середины требует индексированной кучи или ленивого удаления — поэтому на практике часто комбинируют кучу или дерево уровней с хеш-таблицей заявок.
- **Отложенные задачи:** повторы неуспешных платежей, начисления по расписанию, истечение холдов — очередь задач по времени следующего запуска (`DelayQueue` в Java построен на `PriorityQueue`; в Redis для того же часто используют sorted set).
- **Потоковая аналитика:** медиана суммы транзакций или задержки в скользящем окне — две кучи; топ-N клиентов по обороту за день — min-куча размера N.

### Геймдев
- **Поиск пути `A*`:** open set — очередь с приоритетом по `f = g + h`; это самая горячая структура данных в pathfinding.
- **Планирование событий и таймеры:** откаты способностей, баффы, спавн волн, отложенные скрипты — очередь событий, упорядоченная по времени срабатывания (классическая схема дискретно-событийной симуляции).
- **Приоритизация ресурсов:** стриминг текстур и уровней, ограничение числа одновременно звучащих голосов — очередь с приоритетом по важности (расстояние до камеры, громкость), откуда берутся самые важные запросы.

## Типичные ошибки

- Вызывать `q.Push(x)` вместо `heap.Push(q, x)`: метод только добавит элемент в конец среза, без просеивания — инвариант кучи сломан.
- Объявить `Push`/`Pop` с получателем-значением: изменения длины среза потеряются.
- Заполнить срез вручную и забыть `heap.Init` перед первым `heap.Pop`.
- Считать, что срез кучи отсортирован. Гарантирован только корень; чтобы получить порядок, нужно многократно делать Pop.
- Изменить приоритет элемента «на месте» и не вызвать `heap.Fix` — куча молча становится некорректной.
- Для «K наибольших» складывать все n элементов в max-кучу: работает, но O(n) памяти и O(n log n) времени вместо O(K) и O(n log K).
- Ожидать стабильности: куча не сохраняет порядок поступления элементов с равным приоритетом. Если он важен (FIFO среди равных), добавьте в `Less` тай-брейк по порядковому номеру.
