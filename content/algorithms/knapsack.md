## Суть за 30 секунд

Есть рюкзак вместимостью W и n предметов, у каждого вес `wᵢ` и ценность `vᵢ`. Нужно выбрать набор с максимальной суммарной ценностью, не превысив вместимость. В варианте **0/1** каждый предмет берётся целиком или не берётся вовсе.

Ключевая идея: для каждого предмета есть только два варианта — **взять или не взять**. Перебор всех 2ⁿ наборов слишком дорог, но если вес — небольшое целое, можно хранить лучший ответ для **каждой вместимости** от 0 до W и обновлять эту таблицу предмет за предметом.

## История

Задача изучается с конца XIX века; название «задача о рюкзаке» обычно связывают с математиком Тобиасом Данцигом (начало XX века), хотя точное происхождение термина источники указывают по-разному. В 1972 году Ричард Карп включил её в свой знаменитый список 21 NP-полной задачи: полиномиального алгоритма по n и log W не известно. При этом DP за O(n·W) существует — оно **псевдополиномиальное**: полиномиально по *значению* W, но экспоненциально по числу его битов. Для дробного варианта задача решается жадно, а для 0/1 известны приближённые схемы со сколь угодно малой погрешностью (FPTAS).

Любопытный эпизод: в 1978 году Меркл и Хеллман предложили криптосистему на основе сложности рюкзака (subset sum), но уже в начале 1980-х Ади Шамир её взломал — «трудная в худшем случае» задача оказалась лёгкой для конкретных экземпляров.

## Как работает

`dp[i][w]` — лучшая стоимость, если можно использовать первые i предметов и вместимость w. Для предмета i:

- **не берём**: `dp[i−1][w]`;
- **берём** (если `wᵢ ≤ w`): `dp[i−1][w − wᵢ] + vᵢ`.

`dp[i][w] = max(не берём, берём)`. База: `dp[0][w] = 0`. Ответ — `dp[n][W]`.

Здесь предметы (1 кг, 15), (3 кг, 20), (4 кг, 30) и вместимость 4: самый ценный предмет (4 кг, 30) проигрывает паре 1 кг + 3 кг = 35. Именно поэтому жадность «берём самое ценное» или «самое плотное» для 0/1-рюкзака неверна.

**Сжатие до одного массива.** Строка i зависит только от строки i−1, поэтому хватит `dp[w]`. Но перебирать w надо **сверху вниз**: тогда `dp[w − wᵢ]` ещё содержит значение «без предмета i». Если идти снизу вверх, то `dp[w − wᵢ]` уже может включать предмет i, и он возьмётся повторно — а это ровно **неограниченный** рюкзак. Одно направление цикла — два разных алгоритма.

**Восстановление набора.** Нужна полная таблица: идём от `dp[n][W]` вверх; если `dp[i][w] ≠ dp[i−1][w]`, предмет i взят, и `w −= wᵢ`.

## Шаблон на Go

```go
// 0/1-рюкзак: каждый предмет не более одного раза. w — СВЕРХУ ВНИЗ.
func knapsack01(weights, values []int, W int) int {
	dp := make([]int, W+1) // dp[w] — лучшая стоимость при вместимости w
	for i, wi := range weights {
		for w := W; w >= wi; w-- {
			dp[w] = max(dp[w], dp[w-wi]+values[i])
		}
	}
	return dp[W]
}

// Неограниченный рюкзак: каждый предмет сколько угодно раз. w — СНИЗУ ВВЕРХ.
func knapsackUnbounded(weights, values []int, W int) int {
	dp := make([]int, W+1)
	for i, wi := range weights {
		for w := wi; w <= W; w++ {
			dp[w] = max(dp[w], dp[w-wi]+values[i])
		}
	}
	return dp[W]
}
```

Subset sum на битсете — ускорение в ~64 раза: бит s установлен, если сумму s можно набрать. Добавить число x — это `reach |= reach << x`:

```go
// LeetCode 416 Partition Equal Subset Sum.
func canPartition(nums []int) bool {
	total := 0
	for _, x := range nums {
		total += x
	}
	if total%2 != 0 {
		return false
	}
	reach, shifted := big.NewInt(1), new(big.Int)
	for _, x := range nums {
		reach.Or(reach, shifted.Lsh(reach, uint(x)))
	}
	return reach.Bit(total/2) == 1
}
```

Go-детали: `math/big.Int` здесь работает как битсет произвольной длины — сдвиг и OR идут словами по 64 бита. Если ценности большие (до 10⁹) и предметов много, сумма может не влезть даже в `int64` — проверяйте ограничения. Слайс `dp` размера W+1 при W = 10⁹ не создать: это сигнал, что нужен другой подход (DP по ценности, meet-in-the-middle или приближение).

## Сложность

| Вариант | Время | Память |
|---|---|---|
| Полный перебор | O(2ⁿ · n) | O(n) |
| 0/1 или неограниченный, таблица | O(n·W) | O(n·W) |
| То же, один массив | O(n·W) | O(W) |
| Subset sum на битсете | O(n·S / 64) | O(S / 64) |
| DP по ценности (большой W, малые vᵢ) | O(n·Σv) | O(Σv) |
| Meet-in-the-middle (n ≤ 40) | O(2^(n/2) · n) | O(2^(n/2)) |
| Дробный рюкзак (жадно по vᵢ/wᵢ) | O(n log n) | O(1) |

## Когда применять

- «Выбрать подмножество» при **ограничении на сумму** (вес, бюджет, время, память) и максимизировать/минимизировать что-то ещё.
- «Можно ли разбить на две части с равной суммой», «набрать ровно target» — subset sum.
- «Сколькими способами набрать сумму» — счётный рюкзак (Coin Change II, Target Sum).
- Ограничение на вместимость небольшое (≤ 10⁴–10⁵), а n до сотен-тысяч.
- Вариации: **ограниченный** (каждый предмет до kᵢ раз — раскладываем на степени двойки), **многомерный** (вес и объём — LeetCode 474 Ones and Zeroes), **с группами** (из каждой группы не более одного), **дробный** (жадность корректна).

## Где применяется в реальном мире

### Бигтех
- **Распределение ресурсов и бюджетов**: выбор проектов, фич или экспериментов под ограниченный бюджет, людей или вычислительные квоты — классическая постановка capital budgeting в виде 0/1-рюкзака.
- **Заполнение рекламных пауз**: подобрать ролики так, чтобы уложиться в длительность паузы и максимизировать выручку, — рюкзак по времени; в общем виде это стандартная модель в ad-tech.
- **Упаковка контейнеров по серверам**: планировщики (например, Kubernetes со стратегией скоринга `MostAllocated`) решают родственную задачу bin packing — плотнее загрузить узлы CPU и памятью; на практике используются эвристики, потому что точное решение NP-трудно.

### Финтех
- **Выбор монет (coin selection) в Bitcoin Core**: кошелёк подбирает входы так, чтобы сумма максимально точно покрыла платёж и не понадобился выход со сдачей. Для этого используется алгоритм Branch and Bound — перебор с отсечениями для subset sum.
- **Сборка блока майнером**: выбрать транзакции, максимизирующие комиссии, при лимите веса блока — это рюкзак; Bitcoin Core решает его жадным приближением по комиссии на единицу веса с учётом зависимых транзакций.
- **Оптимизация портфеля с целыми лотами**: при бюджете и неделимых лотах непрерывная оптимизация превращается в целочисленную задачу рюкзачного типа.

### Геймдев
- **Инвентарь с ограничением по весу** в RPG и «автоэкипировка» — рюкзак в буквальном смысле.
- **Сборка армии или колоды по очкам**: в стратегиях и карточных играх на юнитов или карты выделяется бюджет очков, а ИИ или подсказчик ищет сильнейшую комбинацию.
- **Выбор уровней детализации (LOD) под бюджет кадра**: ещё в работе Funkhouser и Séquin (1993) выбор LOD для каждого объекта формулировался как задача рюкзака с выбором из групп — максимум качества при ограничении на время отрисовки.

## Типичные ошибки

- В 0/1-рюкзаке на одном массиве перебирать w **снизу вверх** — предметы берутся многократно.
- Жадно брать «самое ценное» или «самое выгодное по vᵢ/wᵢ» в 0/1-варианте — работает только для дробного рюкзака.
- Путать порядок циклов в счётных задачах: монеты снаружи — комбинации, сумма снаружи — перестановки.
- Инициализировать `dp` нулями, когда нужно **ровно** заполнить вместимость: тогда недостижимые состояния должны быть `−∞` (или `-1`), а `dp[0] = 0`.
- Не заметить, что W огромный (10⁹): таблица O(W) не поместится в память, нужен другой подход.
- Сжать таблицу в один массив и потом пытаться восстановить, какие предметы взяты.
