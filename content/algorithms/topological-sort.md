## Суть за 30 секунд

Топологическая сортировка выстраивает вершины ориентированного графа в линию так, что **каждое ребро u → v ведёт слева направо**: u стоит раньше v. Если рёбра — это «надо сделать до», то результат — допустимый порядок выполнения задач.

Аналогия — утреннее одевание: носки до ботинок, рубашка до галстука, а часы можно надеть когда угодно. Таких порядков обычно много, но если зависимости зациклились («чтобы получить опыт, нужна работа, а чтобы получить работу — опыт»), порядка не существует. Поэтому топосорт одновременно и строит порядок, и **проверяет граф на цикл**: он существует тогда и только тогда, когда граф ацикличен (DAG).

## История

Задача пришла из управления проектами конца 1950-х: методы сетевого планирования PERT (созданный для программы ракет «Поларис» ВМС США) и CPM (метод критического пути, разработанный в DuPont) представляли проект как граф работ с зависимостями, и вычисления по нему требовали обхода в топологическом порядке.

В 1962 году Артур Кан опубликовал в Communications of the ACM статью «Topological sorting of large networks» с алгоритмом, который сегодня так и называют — **алгоритм Кана**: многократно выбирать вершины без входящих рёбер. Вариант через поиск в глубину (развёрнутый порядок выхода из вершин) стал классикой после работ Тарьяна о DFS в 1970-х; точное авторство этого варианта приписывают по-разному.

В классическом Unix есть утилита `tsort`, которую использовали в паре с `lorder`, чтобы упорядочить объектные файлы в статической библиотеке так, чтобы компоновщик смог разрешить все ссылки за один проход.

## Как работает

### Алгоритм Кана (BFS по входящим степеням)

1. Для каждой вершины считаем **входящую степень** (indegree) — число невыполненных зависимостей.
2. Все вершины с indegree = 0 кладём в очередь: их можно делать прямо сейчас.
3. Достаём вершину u, дописываем в ответ и «вычёркиваем» её исходящие рёбра: у каждого соседа v уменьшаем indegree. Если стало 0 — v разблокирована, кладём её в очередь.
4. Повторяем, пока очередь не опустеет.

Если в ответ попали **не все** вершины — оставшиеся ждут друг друга по кругу: в графе есть цикл. Именно так решается Course Schedule.

В визуализации — граф учебных курсов. Под узлами — их indegree. Go и Net не зависят ни от чего и стартуют сразу; API разблокируется только после того, как пройдены все три её пререквизита (DS, SQL, Net), а K8s — последней.

Цвета показывают «волны» Кана: зелёные стартуют сразу (indegree 0), синие разблокируются после первой волны и т.д. Вершины одной волны независимы друг от друга — их можно выполнять **параллельно**. Число волн — минимальное число «семестров» или стадий сборки (Parallel Courses).

### Через DFS

Запускаем DFS (с тремя цветами — чтобы ловить циклы) и дописываем вершину в список **в момент выхода** из неё, когда все её потомки уже обработаны. Вершина попадает в список после всего, что от неё зависит, поэтому **развёрнутый** список — топологический порядок. Встретили серую вершину — цикл.

Какой вариант выбрать: Кан естественно даёт уровни (параллелизм), лексикографически наименьший порядок (замените очередь на min-кучу) и проверку единственности порядка (в очереди всё время ровно один элемент). DFS короче в коде, если DFS по графу всё равно уже написан, и удобен для DP «по потомкам».

**DP на DAG.** Почти любая динамика по DAG — самый длинный путь, число путей, критический путь проекта, «самая ранняя возможная дата старта» — считается одним проходом в топологическом порядке: к моменту обработки вершины все её предшественники уже посчитаны.

## Шаблон на Go

```go
// Алгоритм Кана. edges: {a, b} означает «a должно идти раньше b».
// ok == false, если в графе есть цикл.
func topoSort(n int, edges [][2]int) (order []int, ok bool) {
	adj := make([][]int, n)
	indeg := make([]int, n)
	for _, e := range edges {
		adj[e[0]] = append(adj[e[0]], e[1])
		indeg[e[1]]++
	}
	queue := make([]int, 0, n)
	for v := 0; v < n; v++ {
		if indeg[v] == 0 {
			queue = append(queue, v)
		}
	}
	for len(queue) > 0 {
		u := queue[0]
		queue = queue[1:]
		order = append(order, u)
		for _, v := range adj[u] {
			indeg[v]--
			if indeg[v] == 0 {
				queue = append(queue, v)
			}
		}
	}
	return order, len(order) == n
}
```

```go
// DFS-вариант: вершина попадает в список после всех своих потомков;
// развёрнутый post-order — топологический порядок.
func topoDFS(adj [][]int) (order []int, ok bool) {
	const (
		white = iota
		gray
		black
	)
	color := make([]int, len(adj))
	var dfs func(u int) bool
	dfs = func(u int) bool {
		color[u] = gray
		for _, v := range adj[u] {
			if color[v] == gray || (color[v] == white && !dfs(v)) {
				return false // цикл
			}
		}
		color[u] = black
		order = append(order, u)
		return true
	}
	for u := range adj {
		if color[u] == white && !dfs(u) {
			return nil, false
		}
	}
	slices.Reverse(order)
	return order, true
}
```

Топологический порядок встроен в сам Go:

- **Инициализация пакетов:** по спецификации пакет инициализируется только после всех импортированных им пакетов. Внутри пакета переменные уровня пакета инициализируются по зависимостям: на каждом шаге выбирается самая ранняя в порядке объявления переменная, у которой нет зависимостей от ещё не инициализированных, — это топологическая сортировка с тай-брейком по порядку объявления. Цикл даёт ошибку компиляции «initialization cycle».
- **Импорты:** граф импортов обязан быть DAG — «import cycle not allowed». Благодаря этому `go build` может собирать пакеты в топологическом порядке и параллельно компилировать независимые.

## Сложность

| Вариант | Время | Память |
|---|---|---|
| Алгоритм Кана | O(V + E) | O(V + E) — список смежности, indegree, очередь |
| DFS + разворот | O(V + E) | O(V + E) |
| Лексикографически наименьший порядок (Кан + min-куча) | O(V log V + E) | O(V + E) |
| Перечисление всех топологических порядков | экспоненциально (backtracking) | O(V) |

## Когда применять

- В условии есть **«prerequisites», «зависимости», «сначала нужно сделать X»**, «порядок сборки / установки / прохождения курсов».
- **«Можно ли выполнить все задачи»** = нет ли цикла в графе зависимостей (Course Schedule).
- **Восстановить порядок по частичным сравнениям:** Alien Dictionary (из соседних слов словаря выводим «буква a раньше буквы b»), Sequence Reconstruction.
- **«Минимальное число этапов/семестров»** при параллельном выполнении — число волн в алгоритме Кана.
- **Самый длинный путь, число путей, критический путь в DAG** — DP в топологическом порядке.

Вариации: Кан с min-кучей для лексикографического порядка, проверка единственности порядка, топосорт по уровням (Parallel Courses, Minimum Height Trees — «обрезка листьев» как Кан на неориентированном дереве), DFS-вариант с тремя цветами.

## Где применяется в реальном мире

### Бигтех
- **Системы сборки:** Make, Ninja и Bazel строят граф действий (компиляция, линковка, генерация кода) и выполняют его в топологическом порядке, запуская независимые действия параллельно; цикл зависимостей — ошибка сборки.
- **Terraform:** строит граф ресурсов по ссылкам между ними и обходит его с учётом зависимостей: сеть создаётся до виртуальной машины, а независимые ресурсы — параллельно (по умолчанию до 10 операций одновременно). При удалении граф обходится в обратном порядке.
- **systemd:** при загрузке упорядочивает запуск юнитов по зависимостям `After=`/`Before=`; найдя цикл, пишет в журнал «ordering cycle» и разрывает его, отбрасывая одну из задач.
- **Электронные таблицы:** пересчёт ячеек после изменения — в порядке зависимостей формул; циклическая ссылка — тот самый цикл, при котором топологического порядка нет.

### Финтех
- **Пайплайны данных и отчётности:** Apache Airflow запускает задачи по DAG, dbt строит модели в порядке зависимостей, выведенном из `ref()`. Так собирается регуляторная и управленческая отчётность: сырые проводки → агрегаты → витрины → отчёт.
- **Закрытие операционного дня:** начисление процентов → проводки → пересчёт балансов → выписки и отчёты; batch-планировщики описывают эти шаги как DAG заданий и проверяют его на циклы.
- **Расчётные графы в риск- и прайсинг-системах:** справедливая стоимость инструмента зависит от кривых, кривые — от котировок. При обновлении котировки пересчитываются только зависимые узлы, в топологическом порядке, — как в электронной таблице (общая практика построения таких движков).

### Геймдев
- **Frame graph / render graph:** рендер-проходы объявляют, какие ресурсы читают и пишут; движок строит DAG, отбрасывает проходы, результат которых не используется, и упорядочивает остальные. Подход представлен в докладе о FrameGraph движка Frostbite (GDC 2017); в Unreal Engine аналог — Render Dependency Graph (RDG).
- **Планирование систем ECS:** в Bevy системы упорядочиваются по ограничениям `before`/`after` и данным, к которым они обращаются, а независимые выполняются параллельно; в Unity Job System зависимости задач задаются через `JobHandle` и образуют DAG.
- **Деревья технологий и цепочки квестов:** пререквизиты — граф зависимостей; инструменты дизайнеров проверяют, что в нём нет циклов и что каждый узел достижим.

## Типичные ошибки

- Не проверить `len(order) == n` — при цикле алгоритм Кана молча вернёт неполный порядок.
- Перепутать направление рёбер: в Course Schedule пара `[a, b]` означает «чтобы пройти a, нужно сначала b», т.е. ребро **b → a**.
- Потерять изолированные вершины: перебирать только вершины, встречающиеся в рёбрах, а не все n.
- DFS-вариант: дописывать вершину при входе, а не при выходе, или забыть развернуть результат; использовать два цвета вместо трёх и не заметить цикл.
- Alien Dictionary: не обработать случай, когда более длинное слово стоит перед своим префиксом («abc» перед «ab») — это противоречие; добавлять дублирующиеся рёбра и раздувать indegree.
- Считать порядок единственным: тесты, которые сравнивают с одним «правильным» ответом, обычно принимают любой корректный порядок — не стоит подгонять решение под пример.
