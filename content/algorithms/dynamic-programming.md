## Суть за 30 секунд

Динамическое программирование (DP) — это рекурсия, которая **не решает одну и ту же подзадачу дважды**. Если задача распадается на подзадачи, которые многократно повторяются, мы сохраняем их ответы в таблицу и переиспользуем. Наивный перебор за O(2ⁿ) превращается в O(число состояний × стоимость перехода).

Аналогия: спросите человека, сколько будет 1+1+1+1+1 — он посчитает. Допишите «+1» — он ответит «6» мгновенно, не пересчитывая. Он **запомнил** промежуточный результат.

## История

Метод разработал американский математик **Ричард Беллман** в начале 1950-х в корпорации RAND, решая задачи многошагового принятия решений. Ему же принадлежит **принцип оптимальности**: оптимальная стратегия обладает тем свойством, что её «хвост» оптимален для состояния, в которое мы попали.

О названии Беллман рассказал в автобиографии «Eye of the Hurricane» (1984): министр обороны Чарльз Уилсон, от которого зависело финансирование RAND, якобы болезненно реагировал на слово «research», поэтому нужно было название, к которому не придраться. «Programming» тогда означало планирование (как «линейное программирование»), а «dynamic» подчёркивало многошаговость и, по словам Беллмана, это слово невозможно употребить в уничижительном смысле. Историки отмечают, что хронология в этом рассказе не во всём сходится, так что воспринимайте его как авторскую легенду.

## Как работает

DP применимо, когда у задачи есть два свойства:

1. **Перекрывающиеся подзадачи** — рекурсия многократно приходит в одни и те же состояния. Без этого (как в сортировке слиянием) получится обычное «разделяй и властвуй».
2. **Оптимальная подструктура** — оптимальный ответ собирается из оптимальных ответов подзадач. Кратчайший путь обладает ею, а самый длинный простой путь — нет.

**Рецепт проектирования состояния** (самая сложная часть):

1. **Состояние**: что минимально нужно знать о «прошлом», чтобы решать «будущее»? `dp[x]` — минимум монет для суммы x; `dp[i][j]` — ответ для префиксов длины i и j.
2. **Переход**: из каких меньших состояний получается текущее? Обычно «что делаем с последним элементом».
3. **База**: `dp[0] = 0`, пустые префиксы.
4. **Порядок вычисления**: все зависимости должны быть посчитаны раньше.
5. **Ответ**: какая ячейка (или максимум по ячейкам) — ответ.

**Top-down (мемоизация)** — пишем рекурсию по формуле и кешируем результаты. Плюсы: естественно, считаются только нужные состояния. Минусы: глубина стека, накладные расходы на вызовы.

**Bottom-up (табуляция)** — заполняем таблицу циклами от базы к ответу. Плюсы: нет рекурсии, легко сжать память до одной-двух строк. Минус: надо явно продумать порядок.

Coin Change с монетами {1, 3, 4} и суммой 6: жадный выбор 4+1+1 даёт 3 монеты, а DP перебирает все «последние монеты» и находит 3+3.

## Шаблон на Go

Одна задача в двух стилях — Coin Change (LeetCode 322):

```go
// Top-down: рекурсия + мемоизация. Пишется прямо по рекуррентной формуле.
func coinChangeMemo(coins []int, amount int) int {
	const unknown = -2
	memo := make([]int, amount+1)
	for i := range memo {
		memo[i] = unknown
	}
	var solve func(x int) int // -1 = собрать нельзя
	solve = func(x int) int {
		if x == 0 {
			return 0
		}
		if memo[x] != unknown {
			return memo[x]
		}
		best := math.MaxInt
		for _, c := range coins {
			if c <= x {
				if r := solve(x - c); r >= 0 && r+1 < best {
					best = r + 1
				}
			}
		}
		if best == math.MaxInt {
			best = -1
		}
		memo[x] = best
		return best
	}
	return solve(amount)
}

// Bottom-up: заполняем таблицу от маленьких подзадач к большим.
func coinChange(coins []int, amount int) int {
	dp := make([]int, amount+1) // dp[x] — минимум монет для суммы x
	for x := 1; x <= amount; x++ {
		dp[x] = math.MaxInt
		for _, c := range coins {
			if c <= x && dp[x-c] != math.MaxInt {
				dp[x] = min(dp[x], dp[x-c]+1)
			}
		}
	}
	if dp[amount] == math.MaxInt {
		return -1
	}
	return dp[amount]
}
```

Двумерное DP с восстановлением ответа — LCS:

```go
func LCS(a, b string) (int, string) {
	n, m := len(a), len(b) // байты; для Unicode сначала []rune(s)
	dp := make([][]int, n+1)
	for i := range dp {
		dp[i] = make([]int, m+1)
	}
	for i := 1; i <= n; i++ {
		for j := 1; j <= m; j++ {
			if a[i-1] == b[j-1] {
				dp[i][j] = dp[i-1][j-1] + 1
			} else {
				dp[i][j] = max(dp[i-1][j], dp[i][j-1])
			}
		}
	}
	// Восстановление: идём из угла назад по тем же переходам.
	out := make([]byte, 0, dp[n][m])
	for i, j := n, m; i > 0 && j > 0; {
		switch {
		case a[i-1] == b[j-1]:
			out = append(out, a[i-1])
			i, j = i-1, j-1
		case dp[i-1][j] >= dp[i][j-1]:
			i--
		default:
			j--
		}
	}
	slices.Reverse(out)
	return dp[n][m], string(out)
}
```

Go-детали: встроенные `min`/`max` есть с Go 1.21. Рекурсивная замыкающая функция объявляется в два шага (`var solve func...; solve = ...`). Горутины в Go имеют растущий стек, так что глубокая мемоизация редко падает, но память под кадры всё равно тратится — для n ~ 10⁶ предпочитайте bottom-up. Мемо в `map[[2]int]int` удобно, но в разы медленнее слайса: если состояния — небольшие целые, используйте массив.

## Сложность

| Вариант | Время | Память |
|---|---|---|
| Наивная рекурсия | экспоненциальное, например O(2ⁿ) | O(глубина) |
| Общая формула DP | O(состояний × переход) | O(состояний) |
| Coin Change | O(amount · len(coins)) | O(amount) |
| LCS / edit distance | O(n·m) | O(n·m), или O(min(n, m)) без восстановления |
| Сжатие «только предыдущая строка» | то же | меньше на порядок размерности |

## Когда применять

- Просят **число способов**, **минимум/максимум**, **«можно ли»** — и перебор очевидно экспоненциальный.
- Решение — последовательность выборов, и важна только «текущая позиция», а не весь путь.
- Ограничения вида n ≤ 1000–5000 для O(n²) или сумма/вместимость ≤ 10⁴–10⁵ для O(n·S).
- Типовые семейства: **линейное** (лестница, House Robber), **два префикса** (LCS, edit distance), **интервальное** (`dp[l][r]`: лопание шариков, палиндромы), **рюкзак**, **на деревьях** (DFS возвращает пару «взяли/не взяли»), **по маскам** (`dp[mask][i]` для n ≤ 20), **на сетке** (Unique Paths, Minimum Path Sum).
- Если при этом есть доказуемо верный локальный выбор — сначала проверьте жадность: она проще.

## Где применяется в реальном мире

### Бигтех
- **diff и git**: сравнение файлов — это поиск кратчайшего редактирующего скрипта, двойственного LCS. Алгоритм Майерса (1986), используемый git по умолчанию, — оптимизированное DP за O((n+m)·D), где D — число отличий.
- **Исправление опечаток и «Возможно, вы имели в виду»**: расстояние Левенштейна (и Дамерау–Левенштейна) — классическое DP по двум префиксам; применяется в поисковиках, IDE и fuzzy-поиске.
- **Распознавание речи и декодирование сигналов**: алгоритм Витерби (1967) находит самую вероятную последовательность скрытых состояний HMM; также декодирует свёрточные коды в мобильной и спутниковой связи.
- **Вёрстка текста**: алгоритм Кнута–Пласса в TeX выбирает переносы строк, минимизируя суммарную «некрасивость» абзаца, а не жадно заполняя строки.
- **Seam carving** (контентно-зависимое масштабирование изображений, 2007): DP находит «шов» пикселей с минимальной энергией, который можно удалить незаметно.

### Финтех
- **Оценка опционов**: биномиальная модель Кокса–Росса–Рубинштейна (1979) идёт по дереву цен от экспирации к сегодняшнему дню; для американских опционов в каждом узле берётся `max(исполнить сейчас, держать)` — это обратная индукция Беллмана.
- **Оптимальное исполнение крупного ордера**: разбиение объёма по времени с учётом влияния на цену формулируется как DP по «осталось времени × осталось объёма» (классическая работа Bertsimas и Lo, 1998).
- **Сопоставление контрагентов и санкционный скрининг**: нечёткое сравнение имён и реквизитов через edit distance и родственные метрики.

### Геймдев
- **Эндшпильные таблицы в шахматах** (Nalimov, Syzygy): ретроградный анализ — DP от матовых позиций назад, хранящий для каждой позиции точный результат.
- **Таблицы транспозиций** в движках с альфа-бета-поиском — это мемоизация: одна и та же позиция, достигнутая разными ходами, оценивается один раз.
- **ИИ на основе MDP**: value iteration и policy iteration — прямое применение уравнения Беллмана для планирования поведения агентов и в обучении с подкреплением.

## Типичные ошибки

- Состояние не содержит всего, что влияет на будущее (например, забыли «сколько транзакций осталось» или «держим ли акцию»), — ответ неверный, хотя код выглядит правильно.
- Неверный порядок заполнения: читаем ячейку, которая ещё не посчитана.
- Путать «число комбинаций» и «число перестановок»: в Coin Change II внешний цикл по монетам, а не по сумме.
- `math.MaxInt + 1` переполняется в отрицательное число и становится «лучшим» ответом — проверяйте недостижимость до прибавления.
- Мемо, инициализированное нулём, когда 0 — допустимый ответ: заводите отдельный маркер «не посчитано».
- Сжимать таблицу до одной строки, а потом пытаться восстановить ответ — для восстановления нужна полная таблица (или алгоритм Хиршберга).
