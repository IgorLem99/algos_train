## Суть за 30 секунд

Двоичное дерево поиска (BST) — это бинарный поиск, «застывший» в виде структуры данных. Инвариант один: **всё в левом поддереве меньше узла, всё в правом — больше**. Поэтому на каждом шаге поиска мы отбрасываем целое поддерево, как бинарный поиск отбрасывает половину массива.

Главное преимущество перед отсортированным массивом — вставка и удаление без сдвига элементов. Главное преимущество перед хеш-таблицей — порядок: минимум, максимум, «ближайший не больше x», обход диапазона, k-й элемент. Цена — всё это работает за O(h), и если дерево выродилось в «палку», h = n.

## История

Двоичное дерево поиска было придумано независимо несколькими исследователями в конце 1950-х — начале 1960-х; среди них обычно называют П. Ф. Уиндли, Эндрю Бута, Эндрю Колина и Томаса Хиббарда (Хиббард в 1962 году проанализировал удаление — приём с преемником часто называют «удалением Хиббарда»). Единственного автора у идеи нет.

Проблему вырождения быстро начали решать балансировкой:

- **1962** — Г. М. Адельсон-Вельский и Е. М. Ландис опубликовали **АВЛ-дерево**, первое самобалансирующееся BST.
- **1970–1972** — Рудольф Байер и Эдвард Маккрейт (Boeing) предложили **B-дерево** для дисковых хранилищ; в 1972 году Байер описал «симметричные двоичные B-деревья», которые Леонидас Гибас и Роберт Седжвик в 1978 году переформулировали как **красно-чёрные деревья**.
- **1989** — Сесилия Арагон и Раймунд Зайдель предложили **декартово дерево (treap)**, балансирующееся случайными приоритетами; примерно тогда же Уильям Пью предложил skip list как вероятностную альтернативу деревьям.

## Как работает

**Поиск:** начинаем с корня; если цель меньше узла — идём влево, больше — вправо, равна — нашли. Дошли до `nil` — ключа нет.

**Вставка:** идём как при поиске, пока не упрёмся в пустое место, и вешаем туда новый лист. Существующие узлы не двигаются.

**Удаление** — три случая:

1. Лист — просто отрезаем.
2. Один ребёнок — ставим ребёнка на место узла.
3. Два ребёнка — находим **преемника** (минимум правого поддерева: шаг вправо, потом влево до упора), копируем его значение в узел и удаляем преемника из правого поддерева (у него максимум один ребёнок, так что это случай 1 или 2).

Ещё два полезных свойства:

- **In-order обход выдаёт ключи по возрастанию.** Отсюда k-й минимум, BST-итератор (явный стек), проверка корректности.
- **Floor / ceiling** («наибольший ключ ≤ x», «наименьший ключ ≥ x») ищутся за один спуск: идя вправо, запоминаем текущий узел как кандидата на floor; идя влево — как кандидата на ceiling.

Высота случайного BST в среднем O(log n), но вставка уже отсортированных данных даёт цепочку высоты n. Поэтому в реальных системах почти всегда используют **сбалансированные** варианты: красно-чёрные и АВЛ-деревья (повороты после вставки/удаления), treap, а на диске — B/B+-деревья с сотнями ключей в узле, чтобы высота была 3–4 уровня даже для миллиардов записей.

## Шаблон на Go

```go
// Поиск: на каждом шаге отбрасываем одно из поддеревьев.
func search(root *TreeNode, target int) *TreeNode {
	for root != nil && root.Val != target {
		if target < root.Val {
			root = root.Left
		} else {
			root = root.Right
		}
	}
	return root
}

// Вставка: идём как при поиске и вешаем новый узел на найденное пустое место.
func insert(root *TreeNode, val int) *TreeNode {
	if root == nil {
		return &TreeNode{Val: val}
	}
	if val < root.Val {
		root.Left = insert(root.Left, val)
	} else if val > root.Val {
		root.Right = insert(root.Right, val)
	}
	return root // дубликаты игнорируем
}

// Удаление: у узла с двумя детьми берём преемника — минимум правого поддерева.
func remove(root *TreeNode, val int) *TreeNode {
	if root == nil {
		return nil
	}
	switch {
	case val < root.Val:
		root.Left = remove(root.Left, val)
	case val > root.Val:
		root.Right = remove(root.Right, val)
	default:
		if root.Left == nil {
			return root.Right
		}
		if root.Right == nil {
			return root.Left
		}
		succ := root.Right
		for succ.Left != nil {
			succ = succ.Left
		}
		root.Val = succ.Val
		root.Right = remove(root.Right, succ.Val)
	}
	return root
}
```

```go
// Валидация: каждый узел обязан лежать в интервале (lo, hi), который задают
// ВСЕ его предки. nil-границы вместо math.MinInt/MaxInt — чтобы не ломаться
// на граничных значениях.
func isValidBST(root *TreeNode) bool {
	var check func(n *TreeNode, lo, hi *int) bool
	check = func(n *TreeNode, lo, hi *int) bool {
		if n == nil {
			return true
		}
		if (lo != nil && n.Val <= *lo) || (hi != nil && n.Val >= *hi) {
			return false
		}
		return check(n.Left, lo, &n.Val) && check(n.Right, &n.Val, hi)
	}
	return check(root, nil, nil)
}
```

Что есть в экосистеме Go:

- В стандартной библиотеке **нет** упорядоченного map (аналога Java `TreeMap` или C++ `std::map`). Если данные в основном читаются, отсортированный срез + `slices.BinarySearch` / `sort.Search` часто проще и быстрее дерева (кэш-локальность), хотя вставка в него стоит O(n).
- Для динамических упорядоченных данных обычно берут `github.com/google/btree` — in-memory B-дерево; на нём, например, построен индекс ключей в etcd.
- Сам runtime Go использует дерево поиска: в `runtime/sema.go` горутины, ждущие на семафорах, хранятся в сбалансированном дереве (treap), упорядоченном по адресу семафора.

## Сложность

| Операция | Время (сбалансированное) | Время (вырожденное) | Память |
|---|---|---|---|
| Поиск, вставка, удаление | O(log n) | O(n) | O(1) итеративно, O(h) рекурсией |
| Min, max, floor, ceiling | O(log n) | O(n) | O(1) |
| In-order обход / диапазон из k ключей | O(n) / O(log n + k) | O(n) | O(h) стек |
| k-й элемент (узлы хранят размер поддерева) | O(log n) | O(n) | +1 поле на узел |
| Хранение дерева | — | — | O(n) |

## Когда применять

- Во входе дано **BST** — почти всегда решение использует инвариант: отсечение половины дерева (LCA в BST, поиск, удаление), in-order для отсортированного порядка.
- «Ближайший ключ не больше / не меньше x», «следующий по величине», «все ключи в диапазоне [lo, hi]».
- Данные **поступают динамически**, и при этом нужен порядок: скользящее окно с медианой/min/max, календарь бронирований без пересечений (My Calendar), «сколько элементов меньше x справа».
- «k-й наименьший», «BST-итератор с O(h) памятью», «восстановить BST, где два узла переставлены».

Вариации: построение сбалансированного BST из отсортированного массива (середина — корень), дерево с размерами поддеревьев (order statistics), дерево интервалов, преобразование BST в Greater Sum Tree обратным in-order обходом.

## Где применяется в реальном мире

### Бигтех
- **Ядро Linux:** красно-чёрные деревья (`lib/rbtree.c`) повсюду. Планировщик CFS хранил готовые к запуску задачи в rb-дереве по `vruntime` (следующая задача — самый левый узел); EEVDF, заменивший CFS в ядре 6.6, тоже использует дополненное rb-дерево. `epoll` хранит отслеживаемые дескрипторы в rb-дереве.
- **Стандартные библиотеки:** Java `TreeMap`/`TreeSet` — красно-чёрное дерево (так написано в документации); `std::map`/`std::set` в libstdc++ и libc++ — тоже красно-чёрные деревья.
- **Базы данных:** индексы PostgreSQL по умолчанию — B-деревья, кластерный индекс InnoDB в MySQL — B+-дерево. Это обобщение BST: в узле сотни ключей под размер страницы, чтобы минимизировать чтения с диска.
- **etcd** (хранилище состояния Kubernetes) держит индекс ключей в in-memory B-дереве `google/btree`, что даёт range-запросы по префиксу ключа.

### Финтех
- **Книга заявок (order book):** уровни цен хранят в упорядоченной структуре (сбалансированное дерево, `TreeMap` и т.п.): лучшая покупка — максимум среди bid, лучшая продажа — минимум среди ask, новый ценовой уровень вставляется за O(log n). Это распространённая практика в открытых matching engine.
- **Курсы и котировки «на момент времени»:** «курс валюты на момент t» = floor(t) в упорядоченной по времени структуре (`TreeMap.floorEntry`, B-tree-индекс по timestamp в БД).
- **Леджеры и выписки:** «операции по счёту за период» — range scan по B+-tree-индексу `(account_id, created_at)`: спуск к началу диапазона за O(log n) и последовательное чтение листьев.

### Геймдев
- **BSP-деревья:** Doom (1993) и Quake использовали двоичное разбиение пространства, чтобы быстро определить порядок отрисовки стен относительно камеры. Это то же двоичное дерево, только «сравнение» — по какую сторону плоскости лежит точка.
- **k-d деревья:** поиск ближайшего врага, точки спавна или источника света — двоичное разбиение по чередующимся осям с отсечением поддеревьев.
- **Лидерборды и расписания событий:** нужен ранг игрока и топ-N за O(log n) — используют упорядоченные структуры: сбалансированные деревья или skip list (на нём, например, построены sorted sets в Redis).

## Типичные ошибки

- Проверять корректность BST сравнением только с родителем. Дерево «5, справа 6, у 6 слева 3» пройдёт такую проверку (3 < 6), хотя 3 < 5 лежит в правом поддереве корня. Нужны границы от всех предков (или in-order со сравнением с предыдущим значением).
- Использовать `math.MinInt64`/`math.MaxInt64` как «бесконечные» границы — сломается, если такие значения есть во входе. Безопаснее `nil`-границы или `*int`.
- В рекурсивной вставке/удалении забыть присвоить результат: `root.Left = insert(root.Left, v)`, а не просто `insert(root.Left, v)`.
- Удаление с двумя детьми: скопировать значение преемника, но забыть удалить самого преемника из правого поддерева.
- Не договориться о дубликатах (игнорировать? считать счётчиком в узле? класть влево?) — отсюда «пропадающие» элементы.
- Вставлять в несбалансированное BST отсортированные данные и удивляться O(n) на операцию.
